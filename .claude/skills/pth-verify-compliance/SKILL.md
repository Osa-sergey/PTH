# pth-verify-compliance (SK-11)

Сопоставляет требования с тестами и последними свидетельствами. Только читает данные. ИИ-вывод без свидетельства не даёт статуса `verified`.

## Вход

- Ключ проекта, необязательно тип (`FR`, `NFR`, `AC`) или ID.
- `PTH_URL` и `PTH_TOKEN` с правом чтения.

## Шаги

1. Проверь доступ: `sdk/pth me`.
2. Получи соответствие: `sdk/pth compliance <KEY>`.
3. Сгруппируй по статусу: `verified`, `failed`, `stale`, `not_verified`, `no_test`, `excluded`.
4. Для `failed` и `stale` покажи связанные тесты (`tests`) и причину. `stale` значит: требование изменено после последнего свидетельства.
5. Для конкретного ID посмотри контекст: `sdk/pth context <KEY> <ID>`.
6. Итог: сколько `verified` из всех проверяемых и что блокирует готовность (`readiness`).

## Выход

Счётчики по статусам, список блокирующих элементов с ID и статусом, рекомендации: что завести (тест, связь `verifies`, свидетельство).

## Границы

- Только чтение. Не записывай свидетельства и не меняй статусы.
- Не выставляй `verified` сам и не объясняй отсутствие теста тем, что «код работает».
- `excluded` — не потеряно и не проверено, а исключено по обоснованию. Так и пиши.
- Если API вернул ошибку, передай код и текст.
