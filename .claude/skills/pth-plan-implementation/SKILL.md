# pth-plan-implementation (SK-07)

Составляет план по данным PTH. План не повышает статус реализации: «запланировано» не значит «сделано». Только читает данные.

## Вход

- Ключ проекта и список ID требований (`PTH-FR-012`, `PTH-US-004`).
- `PTH_URL` и `PTH_TOKEN` с правом чтения.

## Шаги

1. Проверь доступ: `sdk/pth me`.
2. Для каждого ID собери контекст: `sdk/pth context <KEY> <ID> --depth 1`.
3. Для каждого ID посмотри влияние изменения: `sdk/pth impact <KEY> <ID> --depth 1`. Это то, что надо будет перепроверить.
4. Проверь готовность проверок по ID: `sdk/pth compliance <KEY>` и выбери нужные строки.
5. Составь план:
   - порядок работ (зависимости: сначала то, от чего уточняются остальные);
   - для каждого шага: ID требований, затронутые элементы, что проверить;
   - риски: потерянные user story, требования без тестов, кандидаты на перепроверку;
   - критерий готовности: какие `verified` должны появиться в `compliance`.
6. Не заявляй готовность: укажи, что реализация и проверка ещё не выполнены.

## Выход

План в виде нумерованного списка шагов с ID, рисками и критериями. В конце — список того, чего не хватает в PTH (тесты, связи, приоритеты).

## Границы

- Только чтение, никаких записей и черновиков.
- Не придумывай ID, оценки сроков и объёмы работ, которых нет в данных. Оценку трудозатрат пользователь делает сам.
- Не объявляй требование реализованным по плану.
