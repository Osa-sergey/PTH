# pth-impact (SK-04)

Показывает последствия правки по правилам каталога связей. Только читает данные.

## Вход

- Ключ проекта и ID изменяемого элемента (`PTH-US-004`).
- Глубина 1–3, по умолчанию 2.
- `PTH_URL` и `PTH_TOKEN` с правом чтения.

## Шаги

1. Проверь доступ: `sdk/pth me`.
2. Посмотри карточку изменяемого элемента: `sdk/pth artifact <KEY> <ID>`, чтобы знать текущую ревизию.
3. Расчёт влияния: `sdk/pth impact <KEY> <ID> --depth 2`.
4. Сгруппируй результат по `certainty`:
   - `explicit` — прямое правило каталога, это надо перепроверить;
   - `candidate` — кандидат для проверки, не нарушение.
5. Для каждого элемента покажи путь (`path`), правила (`rule_ids`, основное — `rule_id`) и что проверить (`action`).
6. Пояснения правил — в поле `rules` ответа: код → `title` и `description`. Объясняй правило его названием и описанием из `rules`, а не выдумывай смысл по коду.
7. Полный каталог правил проекта, встроенных и своих, со статусом включения: `sdk/pth impact-rules <KEY>`. Свои правила (`custom`) проекта влияют на результат наравне со встроенными, их тоже объясняй по `title` и `description`.
8. Если `truncated` равно true, так и скажи: список неполный.

## Выход

Список затронутых элементов с группировкой по глубине и уверенности, путь до каждого и действие. Отдельно — что проверить в первую очередь (коммиты и ADR) и что является только кандидатом.

## Границы

- Только чтение. Ничего не меняй и не создавай.
- Не объявляй затронутый элемент нарушенным: по правилам это признак для проверки.
- Не добавляй влияние по смыслу текста, которого нет в связях. Скажи, что такие связи в PTH не заведены.
- Не создавай и не меняй свои правила (`impact-rules`): это делает пользователь в UI на экране «Влияние».
- При ошибке API передай код и текст пользователю.
