# pth-requirements-review (SK-05)

Берёт замечания из PTH (правила детерминированные, на сервере) и объясняет их пользователю. Только читает данные. Правки предлагает, но не вносит.

## Вход

- Ключ проекта (например `PTH`). Необязательно: уровень `error`, `warning` или `info`, ID конкретного требования.
- `PTH_URL` и `PTH_TOKEN` с правом чтения.

## Шаги

1. Проверь доступ: `sdk/pth me`.
2. Получи замечания: `sdk/pth review <KEY>` (или с `--severity error`).
3. Сгруппируй по правилу и покажи счётчики. Порядок важности: `error`, затем `warning`, затем `info`.
4. Для каждой группы объясни, что означает правило и почему это важно. Примеры правил:
   - `LOST_USER_STORY` — user story не уточнена ФТ и не отражена ADR.
   - `NFR_NO_CRITERION` — в нефункциональном требовании нет числа или измеримого критерия.
   - `DUPLICATE_TITLE` — два элемента с одинаковым названием.
   - `FR_NOT_LINKED`, `AC_NOT_LINKED` — нет связи с user story.
   - `NO_PRIORITY` — не указан приоритет.
   - `VAGUE_WORDING` — расплывчатое слово вроде «быстро».
5. Для конкретного ID можно уточнить контекст: `sdk/pth context <KEY> <ID>`.
6. Предложи, какие правки стоит сделать. Если пользователь попросит их внести, переходи к скиллу `pth-change`. Не правь сам.

## Выход

Сводка на русском: счётчики по уровням, топ замечаний с ID, что из этого стоит исправить в первую очередь. Укажи, что это правила, а не суждение о качестве по смыслу.

## Границы

- Только чтение, без черновиков и применения.
- Замечания — это признаки, а не доказательства ошибки. Не утверждай, что требование неверно, по одному правилу.
- Не переписывай формулировки, которых пользователь не просил. Смысл требования определяет пользователь.
- Если API вернул ошибку, передай код и текст пользователю.
