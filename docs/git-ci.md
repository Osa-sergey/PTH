# Git и CI: как подключать

Источник: спека §13.2–13.3 и §14.4. Здесь — что делать на практике.

## Принцип

Сервер не клонирует произвольные URL и не запускает тесты сам. Он:

1. хранит один заранее настроенный путь к репозиторию на проект, доступ только на чтение;
2. принимает от CI или раннера SHA коммита и результаты тестов;
3. проверяет, что коммит существует в этом репозитории. Если да — свидетельство `verified`. Если нет — отказ, если репозиторий не подключён — `pending` (не засчитывается в готовность).

## Шаг 1. Подключить репозиторий (только admin)

```bash
PTH_TOKEN=<admin-token> curl -X PUT http://127.0.0.1:8000/v1/projects/PTH/repo \
  -H "Authorization: Bearer $PTH_TOKEN" -H "Content-Type: application/json" \
  -d '{"path": "/путь/к/локальному/клону"}'
```

Путь должен быть git-репозиторием. Проверить состояние: `GET /v1/projects/PTH/repo`.

## Шаг 2. Выпустить ключ для CI

```bash
PYTHONPATH=server server/.venv/bin/python scripts/create_key.py project PTH "ci-runner" writer
```

Ключ CI — kind `service`, поэтому его прогоны получают уровень доверия `trusted_ci`. Ключ человека даёт `human_recorded`.

## Шаг 3. Прогон на коммите

Локально или в CI:

```bash
PTH_URL=http://127.0.0.1:8000 PTH_TOKEN=<ci-token> \
  python3 sdk/pth_runner.py --project PTH --repo /путь/к/клону --commit <sha> \
  --tests PTH-TEST-001,PTH-TEST-002 --cmd "python3 -m pytest -q"
```

Раннер:

1. резолвит SHA в полный OID в репозитории;
2. распаковывает коммит через `git archive` во временный каталог (рабочая копия не меняется);
3. запускает команду: код 0 — `pass`, иначе `fail`, превышение времени — `blocked`;
4. отправляет результат в `POST /v1/projects/PTH/ci/runs`.

Ограничение: одна команда даёт один результат всем перечисленным тестам. Результаты по каждому тесту нужны отчёт в формате JUnit XML и отдельный парсер (не сделано).

## Что видно в системе

| Ситуация | Результат | Засчитывается в соответствие |
| --- | --- | --- |
| Репозиторий подключён, коммит найден | `verified: true` | да |
| Репозиторий подключён, коммита нет | 422 `COMMIT_NOT_FOUND` | нет, прогон не записан |
| Репозиторий не подключён | `verified: false` | нет (`not_verified`) |
| Ручная запись человеком (`POST /evidence`) | `human_recorded` | да, по политике проекта |

## Пример шага CI

Фрагмент для любого CI-сервиса, где клон уже есть на раннере:

```bash
git fetch origin "$GITHUB_SHA" 2>/dev/null || true
python3 sdk/pth_runner.py --project PTH --repo "$WORKSPACE" --commit "$CI_COMMIT_SHA" \
  --tests PTH-TEST-001 --cmd "python3 -m pytest -q"
```

Переменные CI зависят от провайдера. Конкретный провайдер и webhooks — вне P0 (§13.2).

## Тесты и проверки: как их задавать

Тест в PTH — элемент типа TEST. Хук после каждого коммита берёт список тестов с сервера, отдельный файл в репозитории не нужен (`pth-tests.json` остаётся только запасным вариантом, если сервер недоступен). Создать тест можно в UI: Проверка → Тесты → «Добавить тест», или через API/ChangeSet.

Атрибуты TEST:

| Атрибут | Смысл |
| --- | --- |
| `command` | Аргументы pytest (`tests/test_api.py -k lost`, `файл::тест`, `-m маркер`) или полная команда, начиная с `{python}`. Команда без `{python}` запускается как `{python} -m pytest -q <аргументы>` |
| `workdir` | Папка внутри репозитория, где запускать команду (например `server`) |
| `kind` | Вид проверки: `unit`, `load`, `static`, `security`, `other`. Без значения считается `unit` |
| `artifacts` | Маски файлов и папок с отчётами через пробел: `allure-results report.sarif`. Папка упаковывается в zip |
| `coverage`, `coverage_gaps` | `partial` и чего тест не проверяет: покрытие считается неполным |

Связь с требованием — `verifies` от теста к требованию. В карточке теста видны команда, проверяемые требования, коммиты реализации (`implements`), история файлов теста в Git и запуски по коммитам. Повторные запуски на одном коммите показываются один раз.

## Файлы к запускам

К любому запуску можно приложить файл до 25 МБ: лог, отчёт нагрузочного теста, Allure, SARIF, JSON quality gate. Файл неизменяем, хранится с sha256, скачивается как вложение.

- Хук всегда прикладывает полный вывод команды как `output.log` и файлы, перечисленные в `artifacts`.
- Для внешнего CI: `sdk/pth attach <KEY> <evidence_uid> <файл>`. `evidence_uid` приходит в ответе `POST /ci/runs`.
- API: `POST /projects/{key}/evidence/{uid}/attachments?name=...` (тело — содержимое файла), `GET /projects/{key}/attachments?evidence=...`, `GET /projects/{key}/attachments/{uid}`.

## Что попадает в ПСИ

Черновик ПСИ (Проверка → Черновик ПСИ, вид «Документ» или «Исходный Markdown») содержит:

- сводку: вердикт готовности, счётчики статусов требований и состояний тестов;
- разделы по видам проверки: функциональные, нагрузочные, статический анализ, поиск уязвимостей, прочие;
- по каждому тесту: команду, файлы, проверяемые требования, неполное покрытие, последний запуск (результат, время, коммит, источник), числа из вывода pytest (прошло, упало, не выбрано отбором, время, код выхода);
- приложения последнего запуска со ссылкой, размером и хешем, и сводки:
  - Allure (`allure-results.zip`): результаты по статусам, суммарное время, упавшие;
  - SARIF (SonarQube-экспорт, Semgrep, Trivy, CodeQL, Bandit): находки по уровням, инструменты, частые правила;
  - quality gate SonarQube (`projectStatus`): статус и невыполненные условия;
  - начало или конец текстовых логов;
- таблицу проверок требований с условием из текста требования;
- пробелы с причиной и ограничения отчёта.

Числа в отчёт попадают только из реальных данных. Время ответа, нагрузка и p95 появятся, только если тест напечатал их в лог или приложил отчёт. SonarQube PTH не запускает и не опрашивает: нужен шаг CI, который кладёт SARIF или JSON quality gate в `artifacts`. По HTML-отчёту Allure (`allure-report`) сводки нет, она строится из `allure-results`.

## Чего нет

- Проверки пути и символа из manifest (`code_refs`): функция `path_exists_at` есть, в API не подключена.
- Результаты по каждому тесту из отчёта: нужен парсер.
- Достижимость коммита от baseline и повторное использование свидетельства для нового коммита (§14.4 требует equivalence review).
- Подпись manifest: сейчас доверие к ключу CI, а не к подписи.
