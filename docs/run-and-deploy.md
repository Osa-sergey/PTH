# Запуск и развёртывание PTH

Статус: спецификация v0.1 — проект для обсуждения, реализован срез (API, UI, SDK). Что именно работает, см. [implementation-status](implementation-status.md). Ниже — способы запуска, которые проверены локально (разработка), и схема развёртывания, которая **на сервере не проверялась**.

## Что нужно

- Python 3.11+ (разрабатывалось на 3.13), Node.js 20+ с npm, git.
- Для выделения требований моделью — LM Studio или совместимый сервер (необязательно).

## 1. Локальный запуск для разработки

```bash
git clone https://github.com/Osa-sergey/PTH.git && cd PTH
```

API:

```bash
cd server && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

```bash
cd server && .venv/bin/python -m pth
```

База (`server/pth.db`, SQLite) и миграции создаются при первом запуске. Документация API: http://127.0.0.1:8000/docs.

UI (второй терминал):

```bash
cd ui && npm install && npm run dev
```

Откройте http://127.0.0.1:5173/. Dev-сервер Vite проксирует `/v1` на API (порт 8000).

Оба сервера сразу: `scripts/dev.sh` (API с автоперезапуском и UI).

## 2. Первый вход: ключ доступа

API требует заголовок `Authorization: Bearer <token>`. Токены хранятся в базе только как SHA-256, поэтому токен печатается один раз.

```bash
cd server && .venv/bin/python scripts/create_key.py admin "владелец"
```

Сохраните вывод в менеджере паролей, в репозиторий его не кладите. Вставьте токен в поле токена в левом меню UI (он хранится в `sessionStorage` вкладки и пропадает при закрытии).

Ключ для CI или скрипта на один проект:

```bash
cd server && .venv/bin/python scripts/create_key.py project PTH "ci-runner" writer
```

Роли: `reader` (только чтение) и `writer`. Прогоны с таким ключом получают доверие `trusted_ci`.

## 3. Первые данные

Создать проект и загрузить демо:

```bash
cd server && PTH_TOKEN=<admin-token> .venv/bin/python scripts/seed_demo.py
```

Свою спецификацию можно загрузить в UI: «Данные → Импорт» (таблицы с ID, предпросмотр, черновик, затем применить в «Изменения»). Выделение моделью требует LM Studio.

## 4. Настройки (переменные окружения)

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PTH_DATABASE_URL` | строка подключения SQLAlchemy | SQLite `server/pth.db` |
| `PTH_LLM_BASE_URL` | адрес OpenAI-совместимого сервера модели | из `pth/llm.py` (LM Studio) |
| `LM_API_TOKEN` | токен LM Studio, только в окружении процесса | нет |
| `VITE_PTH_API_URL` | (сборка UI) базовый адрес API | `/v1` |
| `PTH_URL`, `PTH_TOKEN` | для SDK и git-хука | нет |

Токены в файлы репозитория не записываются.

## 7. Развёртывание на сервере (схема)

Не проверялось на реальном сервере; используйте как отправную точку.

1. Поставьте код и зависимости как в п. 1, в `server/.venv`.
2. Запустите API без `--reload`, слушая только localhost, из каталога `server` (процесс должен перезапускаться при падении, например systemd):

   ```bash
   cd server && .venv/bin/python -m uvicorn pth.__main__:app --host 127.0.0.1 --port 8000
   ```

3. Соберите UI: `cd ui && npm ci && npm run build`. Статика окажется в `ui/dist`.
4. Поставьте перед ними обратный прокси с TLS (nginx, Caddy): `/` отдаёт `ui/dist` (с возвратом на `index.html`), `/v1` проксируется на `127.0.0.1:8000`. Тогда UI и API на одном адресе и настройка `VITE_PTH_API_URL` не нужна.
5. Закройте доступ к API снаружи, кроме прокси. Токены выпускайте скриптом `create_key.py` на сервере.
6. Репозиторий кода проекта, с которым сверяются коммиты, должен лежать на этом же сервере (путь задаётся админом, доступ только на чтение).

### Данные и резервные копии

- Все данные в SQLite `server/pth.db` в режиме WAL: рядом лежат `pth.db-wal` (последние записи, ещё не перенесённые в основной файл) и `pth.db-shm`. Копия без остановки сервера: `cd server && .venv/bin/python scripts/backup_db.py` (в `server/backups/`); `cp pth.db` для копии не годится — теряет записи из `-wal`. Восстановление: остановить сервер, удалить `pth.db-wal` и `pth.db-shm`, заменить `pth.db` копией. Если оставить старый `-wal`, SQLite применит его к копии и база будет повреждена.
- PostgreSQL через `PTH_DATABASE_URL` теоретически возможен, но драйвер не входит в `requirements.txt` и на нём не тестировалось.

### Ограничения текущего среза

- Один процесс API; масштабирование на несколько реплик с SQLite не рассчитано.
- Нет Dockerfile и CI-конфигурации самого проекта.
- Спецификация и ADR остаются на статусе «предложено»; DEC-01…13 — рабочие варианты.
